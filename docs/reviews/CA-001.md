### F-0001 — 出力が入力と同じ実体のとき元の証拠ファイルを切り詰める

**根拠:** `make_output_writer` の `File::create(path)` は、既存の出力を直ちに truncate する。`run` はすでに入力を開いてワーカーを起動しているが、入力と出力が同じファイル実体かを確かめない（`src/main.rs:96`、`src/main.rs:474`）。入力のハンドルを先に開いても truncate は避けられない。

**再現:** `HELLO WORLD` と NUL の 12 バイトを入れた一時ファイルに対し、`pstrings -e ascii -j 1 -o input.bin input.bin`。exit 1 / `unexpected EOF while reading chunk` になり、入力は 0 バイトになった。出力を入力へのシンボリックリンク、ハードリンクにした場合も同じ結果だった。

**影響:** 単なる解析失敗でなく入力データを失う。フォレンジック用途では優先して保護すべき条件。

**必要な修正:** truncate より前に同じファイル実体への出力を拒否する。文字列としてのパス比較だけでは別名・リンクを見逃す。同一パス・シンボリックリンク・ハードリンクで入力の内容が維持されるテストが必要。

### F-0002 — 保留中の文字列を考慮せず全体のオフセット順を崩す

**根拠:** `output_merged_chunk` は `ends_at_chunk` のレコードを `pending` に置く一方、それより後の別符号化の完了レコードは即座に書く（`src/outputter.rs:222`）。`process_boundary_records` の局所的な sort と EOF の `drain_pending` では、すでに出力したレコードの順序を戻せない。

**再現:** 入力は UTF-8 の `éABCDéEFGHéIJKL` と NUL。`-e ascii,utf8 -j 1 -c 8` のオフセット列は **2, 8, 0, 14**。同じ入力を `-c 64` で走査すると **0, 2, 8, 14** になる。どちらも exit 0。

**影響:** オフセットで整列した出力というマージ／出力の契約と、チャンクサイズに結果を依存させない契約を破る。出力を順番に処理する利用者は途中で拒否・誤検索しうる。レコード自体の欠落を伴う F-0003 とは区別する。

**必要な修正:** すべての保留レコードを含め、これから確定しうる最小オフセットを考慮して出力順を守る。単一スキャナだけでなく、長さの違う文字列が複数の符号化で重なる入力を CLI から検証する。

### F-0003 — 併用時の境界判定で文字列が消える・分割される

**根拠:** 境界処理は、最初の `starts_at_chunk == false` のレコードに達した時点で境界候補の収集をやめる（`src/outputter.rs:171`）。しかし別の符号化の継続レコードは、先読みのためチャンク先頭より後に始まり、そのレコードより後ろに並びうる。また、空チャンクを先読み済みとして維持する判定は `pending.values().all(...)` であり（`src/outputter.rs:296`）、一つの符号化の終了により、別の符号化の生きている保留レコードまで一緒に flush してしまう。

**再現 A:** UTF-16LE の `ABCD`（8 バイト）に対し、既定の `ascii,utf16le-ascii` で `-c 1 -j 1` を指定すると **出力なし、exit 0**。`-c 2` または `-c 8` では `ABCD` の 1 行を返す。`utf16le-ascii` 単独では 1 バイトのチャンクでも抽出できる。

**再現 B:** UTF-8 の `AB😀CあDEF` と NUL に対し、`-e ascii,utf8 -c 4 -j 1` は **`AB😀Cあ` だけ**を返し、`DEF` が欠ける。同じチャンクサイズでも `-e utf8` 単独なら全文を返す。公開版 v0.1.46 と Target の双方で再現した。

**影響:** 成功扱いのまま文字列が欠落する。単に出力順を整えても直らない。

**必要な修正:** 継続候補の有無と先読み済みの範囲を符号化ごとに判断する。一つのスキャナの非継続レコード／空出力を理由に他のスキャナの保留を終了しない。再現 A/B を含む併用時のチャンクサイズ不変性テストが必要。

### F-0004 — UTF-16LE の偶奇の選別で正しい末尾を落とす

**根拠:** `resolve_parity_overlap` は各チャンクの候補だけを比較し、ASCII だけに見える側を優先する（`src/scanner/utf16le.rs:71`、`:456`、`:510`）。短い末尾フラグメントでは、正しい日本語の上位バイトと NUL をずらして読んだ ASCII が勝ち、境界連結の前に本物の候補を捨てる。

**再現:** 入力は UTF-16LE の `あいうえお` と NUL（12 バイト）。`-e utf16le -f ascii,kanji-jis2,hiragana,katakana -j 1 -c 8` は **`あいうえ`**を返す。`-c 64` は **`あいうえお`**を返す。どちらも exit 0。最後の `お`（U+304A）の上位バイト `30` と続く NUL を奇数位置から `0x0030`（ASCII の `0`）と解釈した候補が、正しい末尾の候補より優先される。

**影響:** 正しい UTF-16LE の入力がチャンクサイズにより異なる文字列になる。誤ったパリティの偽陽性がありうるという既知の制約だけでは、この正しい文字列の欠落を正当化できない。

**必要な修正:** フラグメントの局所的な長さ・ASCII 判定だけで、前のチャンクから続く正しい候補を捨てない。末尾 1 文字・サロゲートペア・偶奇の開始位置を含めて、選別と連結を整合させる。

### F-0005 — 並列完了待ちの FD が無制限に増える

**根拠:** 結果チャネルは `jobs * 2` に制限されるが、出力側は先に完了したすべてのチャンクを `BTreeMap<u64, File>` へ読み出す（`src/main.rs:252`、`:264`）。先頭待ちの間も後続ワーカーが次々に処理を進めるため、チャネルの制限は保持中のファイル数に対する backpressure になっていない。

**再現:** 先頭 1 MiB を `ABCD`＋NUL の UTF-16LE の繰り返し、残りをゼロにした 256 MiB の sparse file。`RLIMIT_NOFILE=64` の子プロセスで `-e utf16le -c 1M -j 4 -o /dev/null` を実行すると、チャンク 61 付近の作成で **`Too many open files`、exit 1**。同じ入力・同じ上限で `-j 1` は exit 0。上限 32 でも同様だった。先頭は多数のレコードを作るため、ゼロだけの後続より処理が遅い。人工的な sleep や実装の変更は使っていない。

**影響:** 正常な入力でも、処理時間の偏りと並列数によって失敗する。保持している一時ファイルのディスク領域も、処理済みだが出力待ちのチャンク数に応じて増える。

**必要な修正:** 未出力チャンク数／先行できる処理範囲に上限を設ける。順番待ちしているチャンクの完了を妨げるデッドロックを作らず、低い FD 上限と不均一な処理時間で検証する。

### F-0006 — 長い文字列の連結が入力サイズに比例してメモリを使う

**根拠:** scanner は run をメモリに持ち、チャンクをまたぐと `append_data` が `String::push_str` / `Vec::extend_from_slice` で `pending` の全文を増やし続ける（`src/record.rs:141`、`src/outputter.rs:536`）。出力時もレコード全体を scratch へコピーする。区切りがなければ入力全体が一つの保留文字列になり、チャンクを小さくしても上限にならない。

**再現:** ASCII の `A` だけの合成入力を `-e ascii -c 1M -j 1 --stats -o /dev/null` で実行。16 MiB の入力で peak RSS **36.88 MiB**、64 MiB の入力で **132.89 MiB**。入力以外の設定は同じ。両方とも exit 0。数値はこの環境での観測値であり他の OS で同じになるとは限らない。

**影響:** README の「huge files に対して約 24 MB/worker」という期待を満たさない入力がある。長い有効な run ではファイル全体の大きさに応じてメモリが増え、大容量入力では OOM になりうる。本試験ではホストを OOM にする試験はしていない。

**必要な修正:** 長い run のデータを保持する方法を、実入力の大きさに耐える形にする。最大長で文字列を切るなど出力の意味を変える案は利用者の判断が必要。まず長い run を含むメモリ使用量の契約を明確にし、実装と説明を一致させる。

### F-0007 — 偶数の指定を入力サイズへのクランプ後に拒否する

**根拠:** 明示したサイズを `min(file_len)` してから、その結果に対し UTF-16LE の偶数制約を検査する（`src/main.rs:49`、`:62`）。入力末尾が奇数長であることと、チャンクの区切り幅が奇数であることが混同される。`auto` は同じクランプをしない。

**再現:** UTF-16LE の `ABCD` に 1 バイトのゼロを追加した 9 バイトの入力。`-e utf16le -c auto` は `ABCD` を返す。`-e utf16le -c 64` は **`--chunk-size must be even when UTF-16LE is enabled`、exit 1**。

**影響:** 明示した幅は偶数で、scanner は最終チャンクの端数を扱えるにもかかわらず、有効な入力を解析できない。ファイルサイズを知らずに固定のチャンクサイズを渡す利用者に影響する。

**必要な修正:** 指定するチャンク幅と最終チャンクの実長を区別する。`auto` と明示した偶数サイズの双方で、奇数長の入力を正しく処理するテストが必要。

### F-0008 — SIGINT の停止をワーカー失敗として報告する競合

**根拠:** SIGINT で `cancelled` が立つとワーカーは送信せず終了する。そのタイミングで `recv_timeout` が `Disconnected` を返すと、出力側はキャンセル済みかを確かめず `UnexpectedEof` を `output_error` に入れる（`src/main.rs:274`）。`run` は後段のキャンセル判定より先にこのエラーを返す。

**再現:** F-0006 の 64 MiB 入力を `-e ascii -c 1M -j 1 -o /dev/null` で起動し、30 ms 後に SIGINT を送った。連続 5 回中 3 回は `cancelled by Ctrl+C`、2 回は `worker result channel closed before chunk N was completed`。いずれも exit 1。再現率と N はスケジューリングに依存する。

**影響:** 停止と非ゼロ終了は成立するが、利用者が要求したキャンセルを別の故障として説明する。

**必要な修正:** キャンセルを観測した後の正常なチャネル切断と、キャンセルされていないワーカー欠落を区別する。

## 再現のための最小コード

以下は合成入力だけを一時ディレクトリへ作る。`PSTRINGS` に Target の実行ファイルの絶対パスを設定してから実行する。出力には観測用に exit code と文字列の Python 表現を出す。

```python
import os
import subprocess
import tempfile
from pathlib import Path

exe = os.environ["PSTRINGS"]
with tempfile.TemporaryDirectory() as work:
    root = Path(work)

    def run(data, *args):
        path = root / "input.bin"
        path.write_bytes(data)
        result = subprocess.run(
            [exe, "-j", "1", *args, str(path)], capture_output=True, timeout=10
        )
        print(args, result.returncode, repr(result.stdout.decode()), result.stderr.decode())
        return path

    # F-0001: own temporary input only; this invocation destroys it.
    path = run(b"HELLO WORLD\0", "-e", "ascii", "-o", str(root / "input.bin"))
    print("input size after same-file output:", path.stat().st_size)

    # F-0002: compare offset order.
    for chunk in ["8", "64"]:
        run("éABCDéEFGHéIJKL\0".encode(), "-e", "ascii,utf8", "-c", chunk)

    # F-0003: mixed scanners versus a single scanner / different chunk widths.
    for chunk in ["1", "8"]:
        run("ABCD".encode("utf-16le"), "-c", chunk)
    for encodings in ["utf8", "ascii,utf8"]:
        run("AB😀CあDEF\0".encode(), "-e", encodings, "-c", "4")

    # F-0004: correct UTF-16LE tail must survive either chunk width.
    for chunk in ["8", "64"]:
        run("あいうえお\0".encode("utf-16le"), "-e", "utf16le",
            "-f", "ascii,kanji-jis2,hiragana,katakana", "-c", chunk)

    # F-0007: both requested chunk widths are valid for this odd-length file.
    for chunk in ["auto", "64"]:
        run("ABCD".encode("utf-16le") + b"\0", "-e", "utf16le", "-c", chunk)
```

F-0005/F-0006/F-0008 の合成入力と実行方法（Unix。大きい入力は一時ディレクトリ内にだけ作る）:

```python
import os
import resource
import signal
import subprocess
import tempfile
import time
from pathlib import Path

exe = os.environ["PSTRINGS"]
with tempfile.TemporaryDirectory() as work:
    root = Path(work)
    path = root / "uneven.bin"
    unit = "ABCD\0".encode("utf-16le")
    with path.open("wb") as handle:
        handle.write((unit * (1048576 // len(unit) + 1))[:1048576])
        handle.truncate(256 * 1048576)

    def limit_files():
        resource.setrlimit(resource.RLIMIT_NOFILE, (64, 64))

    for jobs in ["1", "4"]:
        result = subprocess.run(
            [exe, "-e", "utf16le", "-c", "1M", "-j", jobs,
             "-o", "/dev/null", str(path)],
            capture_output=True, preexec_fn=limit_files, timeout=20,
        )
        print("F-0005", jobs, result.returncode, result.stderr.decode())

    path = root / "long-run.bin"
    for mib in [16, 64]:
        with path.open("wb") as handle:
            for _ in range(mib):
                handle.write(b"A" * 1048576)
        result = subprocess.run(
            [exe, "-e", "ascii", "-c", "1M", "-j", "1", "--stats",
             "-o", "/dev/null", str(path)], capture_output=True, timeout=20,
        )
        print("F-0006", mib, result.returncode, result.stderr.decode())

    for _ in range(5):
        child = subprocess.Popen(
            [exe, "-e", "ascii", "-c", "1M", "-j", "1",
             "-o", "/dev/null", str(path)],
            stdout=subprocess.PIPE, stderr=subprocess.PIPE,
        )
        time.sleep(0.03)
        child.send_signal(signal.SIGINT)
        _, stderr = child.communicate(timeout=5)
        print("F-0008", child.returncode, stderr.decode())
```

## Coverage observations and residual risk

- 各スキャナ単独のテストは多い一方、併用時のチャンク不変性を CLI から確かめるテストが不足している。手で組み立てた中間レコードのテストだけでは F-0002/F-0003 を検出できない。既存 256 テストが通ったことはこれらの不具合を否定しない。
- CI は PR/push で codespell、リリースタグで `cargo test --all-features` を実行する構成。PR 時にもテストを実行することは有用な改善だが、CI 構成だけを独立した Finding にはしていない。
- 今回の再現は Linux 実行の証拠。Windows 固有のファイル共有・リンク・キャンセル・一時ファイル削除の挙動は別途確認が必要。
- 比較試験で一致した符号化にも未知の不具合がないとは言えない。規格とライブラリのすべての境界値を網羅した監査ではない。
- 修正を始める場合、まず F-0001 の入力保護、F-0002〜F-0004 の欠落・並び順の契約を扱い、その後 F-0005/F-0006 のリソース上限を設計するのが妥当。出力の意味を変える選択はこの監査では決めていない。
- upstream への新たな報告・PR の提出、既存 PR #1 の更新はしていない。本報告と registry の初回 publication commit が Campaign Anchor になる。
